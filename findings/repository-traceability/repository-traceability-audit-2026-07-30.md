## Summary of broken-chain patterns

**The single most pervasive broken-chain pattern is the Dashboard column: 15 of 18 capabilities have No for Dashboard.** The main dashboard page (`src/app/(app)/dashboard/page.tsx`) is a generic 3-tab shell (Analytics / To Do / Approval) with no capability-specific data widgets. The construction dashboard shows project-level financials but does not surface site diary entries, RFIs, punch list items, or change orders. No ERP capability (procurement, invoicing, journal entries, payroll, fixed assets, bank reconciliation, credit notes) has any dashboard presence at all. This is a universal gap that affects nearly every business capability regardless of how well-wired the rest of its chain is.

**The second most common gap is the Report column: 10 of 18 capabilities have No for Report, and 6 more are only Partial.** Where reports exist, they tend to be implicit (e.g., the GL serves as an implicit report for journal entries and fixed asset depreciation) or accessible only via the general report engine rather than as a dedicated, prominent report for that capability. Construction capabilities (site diary, RFI, punch list) have zero report coverage. The report engine itself is sophisticated (4-type execution dispatch, 17+ construction reports, financial reports) but its coverage is uneven — it heavily favors project-level financial and progress reporting while leaving operational construction workflows (RFIs, punch lists, site diaries) completely uncovered.

**The third pattern is the Audit Log gap in the construction domain: all four construction workflow services** (`construction-site-diary-service.ts`, `construction-field-workflow-service.ts` for RFIs and punch lists, `construction-change-order-service.ts`) **have zero `logActivity()` calls.** This is a clean split: all ERP services use `logActivity()` from `@/lib/audit` consistently, while all construction services do not. The only exception is the e-signature system for change order approvals, which provides a domain-specific tamper-evident trail but does not cover creation, editing, or other lifecycle events. The `activity-log-service.ts` (scoped to `ai_team_dispatch`) is a red herring for this audit — the real audit mechanism for business operations is `@/lib/audit`'s `logActivity()` writing to the `auditLogs` table, and the construction modules simply haven't been wired to it.

## Gaps identified

1. **Dashboard void (15/18 No):** No capability-specific dashboard widgets exist for any ERP or construction module. The main dashboard is a role-based 3-tab shell with no business-data widgets. The construction dashboard shows project financials only.

2. **Report coverage gaps (10/18 No, 6/18 Partial):** Site diary, RFI, punch list, change orders, credit notes, bank reconciliation, payroll (no dedicated analytics report), HR leave, vendor onboarding, and project creation have no dedicated report.

3. **Construction audit logging vacuum (4/4 construction services lack `logActivity()`):** `construction-site-diary-service.ts`, `construction-field-workflow-service.ts` (RFIs + punch lists), and `construction-change-order-service.ts` have zero `logActivity()` calls. Only the e-signature system provides a partial audit trail for change order approvals.

4. **Bank reconciliation API incomplete:** Service implements import/match/ignore/suggest but the API route only exposes GET (listImports). POST routes for import, match, and ignore are unwired — the UI cannot actually perform reconciliation.

5. **Create Project has no UI page:** `src/app/(app)/projects/page.tsx` returns 404. Project creation is API-only, accessible through the VERIDIAN AI PMS or direct API calls.

6. **Purchase Invoice RBAC gap:** `src/app/api/erp/purchase-invoices/route.ts` POST handler lacks `requirePermissionForUser()` — unlike PO and goods receipt routes which both have it.

7. **Credit Note workflow is shallow:** Only 2 states (draft→submitted), no approval engine integration, no posted/cancelled states — unlike journal entries and fixed assets which both use the shared `startApprovalWorkflow()`.
