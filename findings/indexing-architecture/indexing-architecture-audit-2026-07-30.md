## Detailed Findings Per Index Type

### 1. Source Code Index — **real-but-partial**

**What exists:** `ai-os/FUNCTION_CATALOG.json` in `compliance-tracker` (confirmed present, ~1.6MB). Machine-generated by `ai-os/scripts/extract-function-catalog.mjs` (confirmed present, 8KB) which uses the TypeScript compiler's own AST (`ts.createSourceFile`, parse-only). Scans 1,623 files, parsed all 1,623 with zero failures, extracted 5,019 functions.

**Fields per function:** `name`, `file`, `line`, `kind` (function_declaration/arrow_const/class_method/class_constructor), `exported`, `async`, `class_name`, `params[]` (name, type, optional), `jsdoc_summary`.

**What's missing vs. reference architecture:**
- **No call hierarchy.** The catalog records what each function *is* but not what it *calls* or *is called by*. There is no `calls` or `called_by` field. This is the single most important capability for a source code index per the reference definition ("Go to Definition / Find References / call hierarchy"), and it is absent.
- **No import/reference resolution.** Module-level dependencies are not captured.
- **No cross-file reference tracking.** Changing a function cannot be impact-assessed from this catalog.
- **`jsdoc_summary` is null** for all entries observed (the field exists but is never populated by the generator, which only parses, never type-checks).
- **No class hierarchy, no type/interface catalog, no variable catalog.** Only top-level callables are captured.
- **No LSP or tree-sitter tooling.** The generator uses TypeScript's AST directly at parse-only depth, which is shallower than LSP semantic analysis.
- **No return type information.**
- **No system-level integration.** The JSON file lives in `ai-os/` and is referenced by the wiring registry generator as an input source, but it is not wired into any live application endpoint — it is a build-time artifact.

**Regeneration:** The generator script exists and is mechanically sound (not AI-written). It is not hooked into any CI pipeline or git hook — regeneration is manual. No staleness timestamp or drift-detection mechanism was found for this file itself.

### 2. Database Catalog — **real-but-partial**

**What exists:** `ai-os/DATABASE_CATALOG.json` in `compliance-tracker` (~1.5MB). Machine-generated by `ai-os/scripts/extract-db-schema-catalog.mjs` (confirmed present, 3.8KB) using `drizzle-orm getTableConfig()` introspection. 449 tables, 124 enums, 248 other exports.

**Fields per table:** `export_name`, `table_name`, `schema`, `column_count`, `columns[]` (name, data_type, sql_type, not_null, has_default, primary_key, is_unique, enum_values), `foreign_keys[]`, `indexes[]`.

**Critical nuance — the catalog structure supports FKs and indexes, but the data is nearly empty:**
- Only **7 of 449 tables** (1.6%) have any foreign keys cataloged, and all 7 are in the `erp_*` namespace (item batches, serials, UOM conversions, payslip lines, payslips, salary structure components, salary structures).
- **Zero of 449 tables** have any indexes cataloged.
- This means the Drizzle schema definitions for the remaining 442 tables either do not define foreign keys/indexes at the ORM level, or the introspection script does not capture them from the ORM metadata. Given that 7 tables do have FKs, the script *can* extract them — the near-absence is a schema-level finding, not a catalog-tooling finding.

**What's missing vs. reference architecture:**
- **No views, no triggers, no stored procedures.** The catalog only covers tables and enums.
- **No RLS (Row-Level Security) policies** — a critical gap for a compliance-tracking system.
- **No permissions/roles/GRANT statements.**
- **Not introspected from live database.** The source is the Drizzle TypeScript `schema.ts` file, not `pg_catalog`/`information_schema`. The actual deployed database may have diverged (additional columns from manual ALTERs, different constraint names, etc.).
- **No migration history or schema changelog.**
- **No live-database connection.** This is a static schema-source catalog, not a live DB catalog.

### 7. Dependency Graph — **real-but-partial**

**What exists:** `ai-os/WIRING_ENGINE_REGISTRY_2026-07-25.json` in `claude-control` (6.4MB, confirmed present on `master`). Generated by `scripts/generate_wiring_registry.py` (54KB, confirmed present, ~1,074 lines of real Python). Last generated `2026-07-27T09:36:46Z`.

**Scale:** 7,711 entities across 13 types (5,019 functions, 1,940 files, 444 supabase_tables, 195 ai_roles, 40 scripts, 20 engines, 14 cron_jobs, 10 gateways, 9 governance_docs, 7 github_repos, 6 routes, 4 browser_components, 3 vercel_projects) and 7,962 relationships across ~90 distinct relationship types.

**8 input sources** (confirmed from generator code): DATABASE_CATALOG.json, FUNCTION_CATALOG.json, AI_ROSTER_CATALOG.json, 20_ENGINES_10_GATEWAYS_PHASE_PLAN YAML, ROUTE_REGISTRY_SCHEMA YAML, SOFTWARE_CATALOG.yaml, live `knowledge_engine` SQLite table, live `capability_registry` SQLite table.

**Cross-source entity resolution:** Real. File entities from different sources are de-duplicated via a `path_to_id` map — a file cited by the engine inventory, function catalog, route registry, and knowledge engine collapses into one entity carrying all source references.

**Traversable chains — partial success:**
- **Route-level Screen→API→Code chains work.** Example traced: `route-RT-gratuity_calculator-001` → `originates_at` ChainSelector.tsx → `hops_through` 8 engines/gateways → `terminates_at` payroll-engine.ts. All hops show `VERIFIED_MATCH` with content hashes.
- **Code→DB chains do NOT exist.** No `queries_table`, `reads_from`, or `writes_to` relationship type is defined. Functions link to files (`defined_in`) and engines (`implements_engine`), but never to `supabase_table` entities. Tables link back to their schema definition file, but never to the functions that query them. The reference architecture's example chain (Screen → API → code → DB → queue → notification → dashboard) breaks at the code→DB boundary.

**Query tool limitation:** `wiring_query.py` is a lookup-by-term helper that searches both `wiring_registry` and `knowledge_engine` SQLite tables, but it does NOT resolve `target_entity_id` references to follow a chain. You get flat row matches with raw relationship JSON — traversal requires a second manual query per target, which the script does not perform. It is a search tool, not a graph traversal engine.

**Dual output:** JSON snapshot (6.4MB flat file) + SQLite upsert into `wiring_registry` table (with FTS5 index). Both are idempotent full-snapshot rewrites, not incremental diffs.

### 8. Search Index — **real-but-partial**

**What exists — two distinct search layers:**

**(a) SQLite FTS5 (real-and-live):** `superboss-register.py` implements comprehensive FTS5 full-text search across 9+ virtual tables (`instructions_fts`, `work_items_fts`, `actions_fts`, `system_index_fts`, `log_index_fts`, `knowledge_engine_fts`, `capability_registry_fts`, `wiring_registry_fts`, `umr_tasks_fts`). All content tables have `AFTER INSERT/UPDATE/DELETE` triggers keeping FTS indexes synchronized. The `search` subcommand queries 5 tables simultaneously with a custom `_fts_query()` function (stopword removal, quoted-phrase preservation, hyphenated-term grouping). The `check-duplicate` subcommand queries 4 tables with cross-source deduplication. The `lookup-capability` and `lookup-entity` commands use 2-stage resolution (exact match → FTS keyword).

**(b) pgvector for semantic search (real-but-partially-broken):** Two migrations confirm pgvector infrastructure:
- `0037_wave45_fix_missing_embeddings_vector_column.sql`: Adds `embedding vector(1536)` column to `compliance.embeddings`. The migration's own comment states: "the `embedding` vector column referenced throughout `embeddings.ts` was **never actually created** — Every `storeEmbedding()` call has been silently failing since inception — semantic search has never actually worked in production." This was a critical bug-fix.
- `0083_wave99_vector_search_optimization.sql`: Drops old ivfflat index, creates new HNSW index (m=16, ef_construction=64) on the embedding column, and creates an `embedding_cache` table for deduplication.

**What's missing vs. reference architecture:**
- **No Elasticsearch/OpenSearch/Solr.** Zero references found in any examined file across both repos. The entire real search layer is SQLite FTS5 + Postgres pgvector.
- **Breadth gap.** FTS5 indexes only what has been explicitly registered in superboss-register.sqlite (system_index entries, knowledge_engine artifacts, capabilities, wiring entities). It does NOT index logs, tickets, code content, or dashboards — only metadata *about* those things.
- **pgvector was silently broken from inception** until Wave 45. Even after the fix, the system depends on an external embedding API (OpenRouter), and a documented gap exists where `GROQ_API_KEY` is absent from the Vercel deployment, falling back to a hash-based placeholder that produces meaningless similarity scores.
- **No dedicated search engine** for the breadth the reference architecture describes (names, docs, logs, tickets, code, DB objects, APIs, dashboards as a unified searchable corpus).

### 9. Knowledge Graph — **designed-but-not-built**

**What exists — the mechanism is fully implemented:**
- `register-knowledge` subcommand: INSERTs into `knowledge_engine` table with live file-read `content_hash`, `exists_on_disk`, and `verification_status`. Accepts `--relationships` JSON at insert time, resolving each target path against existing rows to populate `related_artifact_id`.
- `add-relationship` subcommand: Appends an edge to the latest row's `entity_relationships` JSON for a given path, with `--evidence` field. Resolves target against existing rows.
- `query-knowledge` subcommand: FTS5 search over `knowledge_engine_fts` (artifact_path, purpose, tags, entity_relationships) with optional `--tag` filter.
- `verify-knowledge` subcommand: Re-reads live file, recomputes SHA-256, sets `VERIFIED_MATCH`/`HASH_DRIFTED`/`PATH_MISSING`.
- `entity_relationships` stored as a JSON array per row with `{related_artifact_id, related_artifact_path, relationship_type, evidence}`.

**What's missing — the mechanism is thinly populated:**
- The `knowledge_engine` table is populated by `knowledge_registry_multisource.py` (cron, every 6 hours) which registers server-side artifacts. However, the agent analysis of the code and data found **no traversable concept-based chain** for any real VERIDIAN feature.
- The reference architecture's own example — an Invoice-style chain: Invoice Table → Invoice API → Invoice Service → Notification → Email Template → Dashboard → Audit — requires multiple `add-relationship` calls linking these artifacts. The mechanism supports this (the code is correct), but **no such chain was found in the examined artifacts or code**. The knowledge engine rows exist but their `entity_relationships` arrays appear to be populated with only the edges that `register-knowledge --relationships` or `add-relationship` have been explicitly called to create.
- The wiring registry (index type 7) provides a *different* kind of graph — file/function/engine entities with code-level relationships — but it does not store the concept-based, evidence-backed edges the reference architecture's Knowledge Graph definition requires.

**Verdict:** The storage, querying, and verification mechanism for a knowledge graph is real and well-implemented. But the *content* — the actual concept-based chains the reference architecture describes — does not appear to have been populated at scale. The mechanism is designed-and-built; the graph content is aspirational.

### 10. Event-Driven Synchronization — **does-not-exist**

**What was checked:**
- **`veridian-task-watchdog.py`** (19KB, claude-control/master, confirmed present): A systemd timer polling every 60 seconds. Scans active `veridian-worker@*` systemd units, detects stalls (>20 min since last checkpoint) and loops (3 identical checkpoints), performs 3-step auto-recovery (search prior occurrences → apply known fix → escalate to RCA AI task). **It does NOT trigger any index, catalog, or registry update.** It is purely a task-lifecycle monitor and recovery agent.
- **`webhook_receiver.py`** (7KB, claude-control/master, confirmed present): A standalone HTTP server (Python stdlib, zero pip deps) that listens at `POST /webhook/<event_type>` with HMAC-SHA256 verification. On verified POST, dispatches to `scripts/automation_rule_engine.py evaluate-rules --trigger-type webhook.<event_type>`. **It does NOT trigger any index/catalog regeneration.** It dispatches to the automation rule engine, which may or may not trigger further actions. **Critically, it is NOT enabled** — its systemd service is explicitly "present, not enabled" pending Owner security approval for network exposure (documented in `OWNER_DECISIONS_NEEDED_2026-07-23.yaml`).
- **No git hooks** were found in either repo (no `.git/hooks/` content in the repo trees, no `pre-commit`/`post-commit` scripts visible).
- **No CI steps** that trigger catalog regeneration were found (the repos' GitHub Actions or CI configurations were not examined in depth, but no `.github/workflows/` directory was visible in claude-control's tree, and no CI-triggered regeneration is documented in MASTER_INDEX.yaml or superboss-register.py).
- **All catalog/registry regeneration is manual CLI or cron:**
  - `knowledge_registry_multisource.py` — cron, every 6 hours
  - `generate_software_catalog.py` — cron, daily at 04:15 UTC
  - `generate_wiring_registry.py` — manual (no cron entry found)
  - `extract-function-catalog.mjs` / `extract-db-schema-catalog.mjs` — manual (no cron entry found)
  - `system-sync.py` — cron, every 6 hours (checks for drift, does not regenerate catalogs)

**Verdict:** There is no event-driven pipeline where a git push, deployment, or configuration change automatically triggers incremental updates to any of the catalogs/registries. This is the single largest gap versus the reference architecture, which explicitly calls for "a Git commit triggers an event that updates index → search → dependency graph → AI index, incrementally — not continuous full rescans."

## UMR Design Evaluation: Evidence-Based Verdict

### PostgreSQL for authoritative metadata/relationships

**Already substantially exists — wrong storage engine, wrong reachability boundary.**

VERIDIAN's application runs on Postgres (449 tables via Drizzle ORM on Supabase). The current metadata/relationship layer (`superboss-register.sqlite`'s `system_index`, `knowledge_engine`, `capability_registry`, `wiring_registry` tables) is architecturally sound — it has real data, real queries, real FTS5 search, and real drift detection. MASTER_INDEX.yaml's own documentation (`SUPERBOSS_REGISTER.md` was 404, but the MASTER_INDEX itself contains the relevant passage) confirms this system is "architecturally unreachable from the TypeScript/Vercel application code" — a grep for `superboss-register` in `src/` returns zero matches.

**The real gap is not "no metadata layer exists" but "the metadata layer lives in a separate SQLite file on the Claude Code server, unreachable from the Next.js application."** The remediation is: (1) port the 4 key tables to Postgres (schema already well-defined), (2) expose them via API routes in the Next.js app, (3) migrate the CLI-based query interface to API-based queries. This is a consolidation/exposure task, not a design-from-scratch task.

### OpenSearch/Elasticsearch for full-text search

**Not justified by current evidence.**

No reference to Elasticsearch, OpenSearch, or Solr was found anywhere in the examined codebase. The current FTS5 implementation is comprehensive (9+ virtual tables, sync triggers, stopword handling, multi-table search) and is genuinely well-built. The gap is not search technology — it's search *breadth* (FTS5 only indexes what's been explicitly registered, not the full corpus of names, docs, logs, tickets, code, DB objects, APIs, and dashboards). Postgres's own built-in full-text search (`tsvector`/`tsquery`) could extend coverage to application data already in the same database at far lower operational cost than standing up a separate search engine cluster. **Recommendation: extend FTS5/Postgres FTS coverage before introducing a new search engine.**

### pgvector for semantic search

**Already substantially built.**

The `compliance.embeddings` table has a `vector(1536)` column with an HNSW index. The `embedding_cache` table provides deduplication. RLS policies are configured. The critical bug (missing column from inception) was fixed in Wave 45 and the index was optimized in Wave 99. The remaining gap is operational (embedding API key availability in Vercel deployment), not architectural. This piece is done.

### Graph database / graph tables in Postgres

**Mechanism exists, needs porting — not designing from scratch.**

The `knowledge_engine` table's `entity_relationships` JSON column and the `wiring_registry` table's `relationships` JSON column both implement graph-like structures. The `add-relationship` subcommand has correct path-resolution logic and evidence tracking. What's missing: (1) the content is thinly populated (no real Invoice-style chains found), (2) the graph lives in SQLite not Postgres, (3) traversal is not supported (wiring_query.py is lookup-only). The migration path is: port the JSON relationship columns to Postgres, optionally adopt Postgres's `ltree` extension or a dedicated graph table pattern, and build a real traversal query interface. The relationship model and schema design already exist — they need a new storage backend and a traversal API, not a new conceptual design.

### Filesystem/Git watchers for event-driven incremental updates

**Does not exist in any form.**

As documented in finding #10, all catalog regeneration is manual CLI or cron. No git hooks, no CI-triggered regeneration, no file watchers, no webhook-triggered index updates. The watchdog polls task status; the webhook receiver is built but not deployed and doesn't trigger index updates anyway. This is the piece that would need to be designed and built from scratch.

### Overall UMR Verdict

**Partially — 2 of 5 pieces are already substantially built, 2 need consolidation/porting rather than new design, and 1 (event-driven sync) does not exist.**

| UMR Component | Status | What Needs to Change |
|---------------|--------|---------------------|
| PostgreSQL for metadata/relationships | Exists in SQLite, needs porting to Postgres + API exposure | Port 4 tables to Postgres, expose via Next.js API routes, replace CLI queries with API queries |
| OpenSearch/Elasticsearch for full-text search | Not needed — extend existing FTS5/Postgres FTS | Drop this from the target; extend FTS5 coverage breadth and add Postgres tsvector for application-data search |
| pgvector for semantic search | **Substantially built** | Fix embedding API key availability; no architectural change needed |
| Graph tables in Postgres | Mechanism exists in SQLite, needs porting + content population | Port relationship data to Postgres, build traversal API, populate real concept chains |
| Filesystem/Git watchers for event-driven sync | **Does not exist** | Design and build from scratch: git hooks or CI steps triggering incremental catalog updates |
